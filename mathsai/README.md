# MathsAI

Automated KS3/KS4 Edexcel mathematics teaching system for a single teacher — lesson planning, worked examples, and tiered practice questions, generated by Claude and cached in SQLite to control API cost.

All 9 implementation phases from `CLAUDE.md` are complete, plus a tenth piece of work not in the original plan: single-password authentication and public deployment, added once it became clear the app had to be reachable from a locked-down school laptop that cannot join a tailnet. This README covers the full system rather than growing incrementally per phase.

## What MathsAI does

- Browse the full KS3/KS4 Edexcel mathematics curriculum via a topic dashboard, grouped by strand
- Generate a complete lesson package per topic (notes, worked examples, key vocabulary, common errors) on first view, cached in SQLite from then on
- Generate three tiers of practice questions (Foundation, Developing, Extending) with answers and mark schemes, cached the same way
- Track which topics have been taught, to which class, and when
- Export lesson content and questions to print-friendly PDF
- Every piece of AI-generated content carries a `reviewed` flag — new content is visibly unchecked until a teacher marks it reviewed, since self-verification by the model isn't a reliable substitute

## Tech stack

- Python 3.11, FastAPI, Uvicorn
- SQLite via SQLAlchemy (WAL mode enabled)
- Alembic for migrations, starting from `0001_initial_schema`
- `python-dotenv` for local `.env` loading
- `services/ai_service.py` — single source of truth for Anthropic API calls (`claude-sonnet-5`), with a 30s timeout and one retry on timeout/429/5xx per call, and structured logging of topic_id/difficulty/duration/token count on every call
- `weasyprint` for server-side PDF export, `markdown` for converting lesson notes to HTML before rendering
- Single-password authentication in `backend/auth.py` — stdlib scrypt hashing, a signed session cookie via Starlette's `SessionMiddleware`, and a login gate in front of every route
- `pytest` + `httpx` for testing, with the Anthropic client mocked via `unittest.mock` — 111 tests, none ever call the real API
- React 19 + Vite + Tailwind CSS v3 + React Router, via Axios (`frontend/src/api/client.js`)
- `react-markdown` for rendering AI-generated lesson notes

## API route reference

All routes are prefixed `/api`. Full request/response shapes are in `backend/schemas.py`.

| Route | Method | Purpose |
|---|---|---|
| `/topics`, `/topics/ks3`, `/topics/ks4` | GET | List topics, optionally filtered by key stage |
| `/topics/search?q=` | GET | Search topics by name |
| `/topics/{id}` | GET | Single topic detail (404 if missing) |
| `/lessons/{topic_id}` | GET | Lesson package — cache hit, or generate-and-cache on miss |
| `/lessons/{topic_id}/refresh` | POST | Force regeneration (writes a `regeneration_log` row) |
| `/lessons/{topic_id}/review` | POST | Mark the cached lesson reviewed |
| `/questions/{topic_id}/{difficulty}` | GET | Question set for one tier (`Foundation`/`Developing`/`Extending`) |
| `/questions/{topic_id}/{difficulty}/refresh` | POST | Force regeneration for that tier |
| `/questions/{topic_id}/{difficulty}/status` | GET | Reviewed/generated_at metadata only — never triggers generation |
| `/questions/{topic_id}/{difficulty}/review` | POST | Mark that tier's cached questions reviewed |
| `/progress` | GET, POST | List / log a teaching entry |
| `/progress/topic/{topic_id}` | GET | Teaching history for one topic |
| `/progress/{id}` | DELETE | Remove a teaching log entry |
| `/export/lesson/{topic_id}/pdf` | GET | Lesson notes + worked examples + vocabulary + common errors as PDF |
| `/export/questions/{topic_id}/pdf` | GET | All three difficulty tiers as one PDF |
| `/health` | GET | `{"status": "ok"}` — uptime / platform health probe |
| `/auth/login` | POST | `{"password": "..."}` → sets the session cookie. 401 on a wrong password, 429 when throttled |
| `/auth/logout` | POST | Clears the session |

Every route above requires a session except `/health` and `/auth/login` — see Network access and authentication. Unauthenticated API calls get `401`; unauthenticated page requests get a `303` to `/login`.

Error handling is consistent across routers: 404 for a missing topic, 422 for an invalid difficulty tier (rejected by a `Literal` path type before the route body runs), 503 when the Anthropic API fails after its internal retry, 500 for a PDF rendering failure.

## Local setup

### Backend

WeasyPrint (PDF export) needs Pango, Cairo, and GDK-Pixbuf as native libraries — install them first, e.g. on macOS: `brew install pango cairo gdk-pixbuf`. No extra step is needed for Docker; these install via `apt-get` there.

```bash
cd mathsai/backend
python3.11 -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt

cd ..
cp .env.example .env   # fill in a real ANTHROPIC_API_KEY to use lesson/question generation

cd backend
alembic upgrade head
uvicorn main:app --reload
```

Then visit `http://localhost:8000/api/topics` to confirm the full curriculum list loads.

### Frontend

```bash
cd mathsai/frontend
npm install
npm run dev
```

Visit `http://localhost:5173` — the dev server proxies `/api/*` requests to `http://localhost:8000`, so the backend must be running too.

## Force-refreshing cached content

Every lesson and question tier is generated once and cached — normal use never re-calls the API for content already generated. To force fresh content (e.g. the AI made a mistake, or the curriculum reference changed):

- In the UI: the **Regenerate** button on the Lesson page, or **Regenerate Questions** on the Questions page. Both open an on-brand confirmation dialog ("This will use API credits — continue?") before doing anything, since this is the one action in the app that spends money on a single click.
- Directly via the API: `POST /api/lessons/{topic_id}/refresh` or `POST /api/questions/{topic_id}/{difficulty}/refresh`.

Every force-refresh — regardless of whether generation then succeeds or fails — writes a row to the `regeneration_log` table (`topic_id`, `content_type`, `timestamp`), so accidental repeated clicks are visible after the fact even though the confirmation dialog already guards against them at the point of click.

## The reviewed workflow

New or refreshed content is never automatically trusted: `lesson_cache` and `question_cache` rows are written with `reviewed=False`, and the Lesson/Questions pages show an amber "Not yet checked" marker with a **Mark reviewed** button until a teacher explicitly clicks it. This exists because asking the model to double-check its own working isn't a reliable correctness check (see `CLAUDE.md` — Production Hardening → Validating AI output) — a qualified teacher reading the content before it reaches a classroom is the one dependable check available here.

## Adding new curriculum topics

The full KS3/KS4 taxonomy lives as a static Python list in `backend/services/curriculum.py` (`CURRICULUM_TAXONOMY`) — there's no admin UI for this, since the taxonomy is fixed reference data, not user content. To add a topic:

1. Add an entry to the appropriate key stage/strand list in `CURRICULUM_TAXONOMY` (`key_stage`, `strand`, `topic_name`, `edexcel_ref`, `difficulty_band`).
2. Restart the backend (or redeploy). `seed_topics()` runs on every startup but only inserts rows for topics not already present by name — it never duplicates existing rows and never triggers AI generation for the new entry (content still generates lazily on first view, exactly like any other topic).

## Docker setup

This is the deployment path — a single container serving both the built frontend and the API on one port.

```bash
cd mathsai
cp .env.example .env   # fill in a real ANTHROPIC_API_KEY
mkdir -p data           # the SQLite file lives here, on a bind-mounted volume — see below
docker compose up --build
```

Visit `http://localhost:8000` — the frontend, API, and PDF export all work from this one address. `GET /api/health` returns `{"status": "ok"}`.

**Persistence**: `docker-compose.yml` mounts `./data` (relative to the `mathsai/` directory) to `/app/data` inside the container, and `DATABASE_URL` is set to `sqlite:////app/data/mathsai.db`. The `.db` file is the only copy of everything generated and taught — **back it up before pulling a new image or running a migration** (see Database migrations below). Never deploy this to a platform whose filesystem resets on redeploy (some free tiers) without pointing `DATABASE_URL` at that platform's own persistent volume equivalent instead.

**Rebuilding after a code change**: `docker compose up --build` (add `-d` to run in the background). Migrations run automatically on every container start via `docker-entrypoint.sh` (`alembic upgrade head` before `uvicorn`), so a schema change just needs a rebuild + restart, not a manual migration step.

## Network access and authentication

This was originally resolved as Tailscale-only with no password layer, on the reasoning that the tailnet was the perimeter so the app needed no auth of its own. That premise no longer holds: the app has to be reachable from a school laptop that is MDM-locked and cannot join a tailnet, so it is publicly hosted and the perimeter moved into the application.

Authentication is therefore a single password, implemented in `backend/auth.py`:

- The password is never stored — only a salted **scrypt** hash in `APP_PASSWORD_HASH`, generated by `generate_password_hash.py`.
- A signed session cookie (`HttpOnly`, `SameSite=Lax`, `Secure` in production, 30-day lifetime) keeps you logged in, so this is not a daily friction.
- **Every** path is gated except three: `/login`, `/api/auth/login`, and `/api/health` (the platform's health probe). `/assets/*` is gated too, so an unauthenticated visitor cannot even download the React bundle — the login page is deliberately server-rendered HTML living outside the SPA.
- API routes answer `401` to an unauthenticated caller; page routes redirect to `/login`.
- Failed logins are throttled to 10 per 15 minutes per IP. This counter is in-memory, so it resets on restart and does not span processes — acceptable for one user on one container, and stated plainly rather than oversold.

The threat this defends against is specific: an open public URL lets any passer-by hit `force_refresh` on 74 topics, each a metered Anthropic call billed to your key. This is cost control and privacy for one known user, not a multi-tenant identity system.

### Fail-closed by design

Setting `ENVIRONMENT=production` makes `APP_PASSWORD_HASH` and `SECRET_KEY` mandatory: without them the app **refuses to start**, with an error naming what is missing. That is deliberate. The mistake it prevents — deploying to a public URL with auth silently switched off — is invisible until the bill arrives, whereas a crash on boot is immediate and obvious.

Locally, leaving `APP_PASSWORD_HASH` unset keeps the app open with no login, so the existing dev loop is unchanged.

## Running online

Deployed to Render from `render.yaml` at the repository root. Railway works the same way; only the blueprint file differs.

**1. Generate a password hash** (the password itself is read via `getpass`, so it never reaches your shell history):

```bash
cd mathsai/backend
source .venv/bin/activate
python generate_password_hash.py
```

Copy the printed `APP_PASSWORD_HASH=...` value.

**2. Cap your API spend first.** In the [Anthropic Console](https://console.anthropic.com/settings/limits), set a monthly spend limit on the key you will deploy with. Auth keeps strangers out; a spend cap is what protects you from any runaway, including your own mis-click. Do this *before* the app is reachable, not after.

**3. Deploy.** Push the repo, then in Render choose **New → Blueprint** and point it at the repository. `render.yaml` already specifies the Dockerfile, a 1 GB persistent disk at `/app/data`, the `/api/health` health check, and the Frankfurt region.

**4. Set the three secrets** in Render's dashboard (they are marked `sync: false` in the blueprint precisely so they are never committed):

| Variable | Value |
|---|---|
| `ANTHROPIC_API_KEY` | your key, from the Console |
| `APP_PASSWORD_HASH` | the hash from step 1 |
| `SECRET_KEY` | Render generates this automatically — leave it alone |

**5. Add your domain** under Settings → Custom Domains and follow the DNS instructions. TLS is issued automatically.

**6. Test it from the school laptop before you depend on it.** School web filters are aggressive and frequently block newly-registered domains. If the URL is blocked, that is a conversation with your IT team, not a code change — and you want to have it in advance, not the night before an observation.

### The persistent disk is not optional

`render.yaml` mounts a disk at `/app/data`, which is where `DATABASE_URL` points. Without it the SQLite file sits on ephemeral container storage and **every generated lesson, question set, and teaching log entry is destroyed on each redeploy** — silently, with the app still appearing to work. A disk also requires a paid instance type; the free tier cannot mount one.

Note that a disk pins the service to a single instance. That is correct here — SQLite has one writer — but it does mean this design cannot be horizontally scaled without changing databases.

### Backups

The disk is persistence, not a backup. To pull a copy down:

```bash
render ssh mathsai       # or use the dashboard shell
# then, from your machine:
scp <render-host>:/app/data/mathsai.db ./mathsai-backup-$(date +%F).db
```

Do this before any migration, and periodically once it holds a term of real work.

### A note on what you put in it

The app stores no pupil data by design — topics, generated content, and a teaching log whose `class_label` is a group name like `Year 9 Set 2`. Keep it that way: no pupil names in `class_label` or the notes field. That mattered little when the database sat on your own laptop; it matters more now it lives on third-party infrastructure.

## Running tests

Locally:

```bash
cd mathsai/backend
source .venv/bin/activate
pytest
```

Tests never call the real Anthropic API — `ai_service` is mocked via `unittest.mock` in every test that exercises `cache_service`/`ai_service`. `conftest.py` points `DATABASE_URL` at a throwaway SQLite file before the app is imported, so running tests never touches your real dev database.

In CI: `.github/workflows/test.yml` runs the same suite on every push/PR touching `mathsai/backend/`, using a dummy `ANTHROPIC_API_KEY` so it runs with no real key and no cost. It installs WeasyPrint's native dependencies via `apt-get` first, since the export tests exercise real PDF rendering (with `cache_service` mocked, not the renderer).

There's no frontend test suite — at this scale, the per-phase manual browser verification (Playwright-driven, screenshotted) that was used throughout development is what stands in for it; see `CLAUDE.md` → Production Hardening → Testing strategy for the reasoning.

## Database migrations

Alembic manages all schema changes — never a manual `ALTER TABLE`. The full Phase 1 schema is captured in `0001_initial_schema`; every change since (including the `reviewed`/`regeneration_log` fields Phase 9 uses) was already part of that baseline.

**Before running any migration against a database that holds real content, back up the `.db` file first**:

```bash
cp mathsai.db mathsai.db.bak            # local dev
cp data/mathsai.db data/mathsai.db.bak  # Docker deployment
```

Common commands (run from `mathsai/backend`, with the venv active):

```bash
alembic upgrade head                      # apply all pending migrations
alembic revision -m "describe the change" # create a new empty revision to edit by hand
alembic downgrade -1                      # roll back one revision
alembic current                           # show which revision the database is on
```

## Model note

`CLAUDE.md` originally specified `claude-sonnet-4-6`, which is not a valid Anthropic model ID. This project uses **`claude-sonnet-5`** instead, wherever the AI service is implemented.
